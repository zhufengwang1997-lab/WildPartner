# 《荒原伙伴》02 · 技术选型

> **更新时间：2026-11-24 10:20（悉尼）**，对应 v1.0.0（a47a731）。
> 每一条都按同一个格式：**选了什么 → 还有哪些备选 → 为什么选它 → 代价 → 以后要换怎么换**。
> 依据：`docs/DECISIONS.md`（决策记录，带日期）、代码注释、各评估报告。标 ❓ 的是没有书面记录、靠推断的，面试时说"我的判断是……"。

面试官问"为什么这么选"时，最好的回答结构永远是：**约束是什么 → 比较了什么 → 取舍了什么 → 代价我知道，而且留了退路。** 下面每条都按这个结构写。

## 1. Unity 6.3 + URP，而不是 HDRP

| 项 | 内容 |
|---|---|
| 选了 | Unity 6000.3.28f1（6.3 LTS）+ URP 17.3 |
| 备选 | HDRP（高清渲染管线）；Unity 6.0 LTS |
| 为什么 | ① **要跨平台**：开发机是 Mac（Metal），测试机是 RTX 5060 Ti 和 GTX 1070 Ti（DX12）。URP 覆盖面最广，也能在老显卡上跑得动。② **画风是卡通**：不需要 HDRP 的物理光照、体积云这些重型功能。③ **URP 17 自带 STP 和 FSR 1**，可以直接作为超分后端。④ 6.3 是本机已装的 LTS 版本（DECISIONS 11-22）。 |
| 代价 | URP 没有内置 DLSS（HDRP 在 Windows 上有），所以 DLSS 只能走 NVIDIA 模块或自写插件——这是 DLSS 只做设计的原因之一。URP 的高端特性（光追等）也更少。 |
| 以后要换 | 超分接口本身不依赖 URP 的具体类，后端才依赖。换 HDRP 时：游戏侧着色器要重写（Toon 着色器的 Pass 结构是 URP 的），超分只需新写 HDRP 版后端，选择器和游戏层不动。 |

> 类比：开连锁小吃店，选了一套"小而全、哪都能开"的标准厨房（URP），而不是只适合大酒楼的重型厨房（HDRP）。

## 2. Forward+ 渲染路径

| 项 | 内容 |
|---|---|
| 选了 | URP 的 Forward+ |
| 备选 | Forward（传统前向）、Deferred（延迟渲染） |
| 为什么 | ① 场景里灯不少：壁灯、壁炉、夜晚的灯笼、蝴蝶发光。传统 Forward 每个物体有灯数上限；Forward+ 把屏幕分成小格子，每格只算影响它的灯，没有这个上限。② **GPU Resident Drawer（GRD）要求 Forward+**（Unity 的限制），选 Forward+ 才能做阶段 4 的 GRD。③ 和透明物体（水、粒子）、自写卡通着色器配合比 Deferred 简单。 |
| 代价 | 需要深度预通道和灯光分格的计算，有固定开销；屏幕上灯很少时比纯 Forward 略贵。 |
| 以后要换 | 管线资源里一个选项。自写着色器已经有 DepthOnly / DepthNormals Pass，换 Deferred 还要给 Toon 加 GBuffer Pass。 |

> 类比：Forward+ 像把大厅分成区域，每个区域的服务员只管自己区域的几桌客人；传统 Forward 是每个服务员要记住全场所有灯的位置。

## 3. 自写 Toon（卡通）着色器

| 项 | 内容 |
|---|---|
| 选了 | 自写 HLSL 着色器 `WildPartner/Toon`（公共代码在 `ToonCommon.hlsl`），所有不透明物体共用 |
| 备选 | URP Lit + 后处理做风格化；Shader Graph 连一个卡通着色器；商店里买现成的卡通着色器 |
| 为什么 | ① **要控制每一个 Pass**：ForwardLit、ShadowCaster、DepthOnly、DepthNormals、**MotionVectors**。超分要的运动向量必须包含风吹动的位移，Shader Graph 和大多数现成着色器做不到"用上一帧的风动时间算上一帧的位置"。② **性能友好**：参数全部放在 `UnityPerMaterial` 常量缓冲里，兼容 SRP Batcher（减少 CPU 设置开销）；带 DOTS Instancing 声明，兼容 GRD。③ 风格：色阶化明暗 + 蓝紫阴影 + 边缘光 + 可选风动。 |
| 代价 | 所有 Pass 自己维护；URP 升级时可能要跟着改。地形（ToonTerrain）没有 DOTS 变体。 |
| 以后要换 | 只要新着色器也提供 MotionVectors Pass 和同样的风动时间约定（`_WP_WindTimePrev`），超分侧不受影响。 |

> 类比：买成衣 vs 定做西装。定做（自写）麻烦，但每个口袋（Pass）都在你想要的位置——尤其是"运动向量"这个口袋，成衣上没有。

## 4. 草用 GPU 实例化，而不是 Unity Terrain 自带的草

| 项 | 内容 |
|---|---|
| 选了 | `GrassRenderer`：把地面切成 7 m 一块，每帧把镜头附近的块用 `Graphics.RenderMeshPrimitives` 提交（GPU 实例化：一个实例 = 0.25 m 格子里的一簇草），Unity 按每块的包围盒做视锥剔除 |
| 备选 | Terrain 自带的细节草；把草做成普通物体摆放；Compute Shader 全 GPU 生成和剔除 |
| 为什么 | ① 草叶形状、风、主角推草都要自己控制。② **运动向量**：超分需要草的真实运动，自己的着色器才能写。③ 密度、高度、枯黄由烘焙贴图驱动，和地形共用一张地面色块图，颜色衔接自然。④ 比"每根草一个物体"便宜得多，比全 Compute 方案简单。 |
| 代价 | ① 块的选择在 CPU 上做，有 CPU 开销（M5 Max 上草地约 0.7–1.4 ms，见特效开销清单）。② `RenderMeshPrimitives` 绘制**不走 GRD**，GRD 帮不到草。③ 远处草的 LOD 和淡出要自己写。 |
| 以后要换 | 换成 Compute Shader 做剔除 + `RenderMeshIndirect`，把块的选择也搬到 GPU（这是"CPU 偏高"问题的下一步优化方向）。 |

## 5. 树和道具：Tripo 生成 + Blender 处理和绑骨

| 项 | 内容 |
|---|---|
| 选了 | 用户在 Tripo 网页上生成模型（只用生成，**不用 Tripo 的绑骨和动画**）→ `tools/blender/process_tripo.py` 批处理：**先焊接重合顶点再减面**、统一尺寸和原点、导出 FBX + 贴图；角色骨骼和动作用自写 Blender 脚本（女巫 27 根骨骼含头发和裙摆，猫单独绑） |
| 备选 | 资源商店买模型；手工建模；Mixamo 自动绑骨；Tripo 自带绑骨 |
| 为什么 | ① 风格统一（同一个生成器）；② 时间：3 天内一个人做不出 20+ 个模型；③ 批处理脚本可重复执行；④ 绑骨不用自动权重：Tripo 网格是成千上万个碎片，Blender 的自动权重会把腿和裙子粘在一起，所以按身体区域手写权重规则。 |
| 代价 | ① 原模型约 190 万三角面，必须大幅减面，减过头会"像马赛克"（见 05 的案例）。② 没有现成动画，动作全靠脚本写曲线。③ 骑鹿没有专门的骑乘动作。 |
| 以后要换 | 处理脚本只认 GLB 输入，换任何模型来源都走同一条管线。 |

> 类比：AI 给你捏好了泥人（Tripo），你自己装骨架、穿线让它动（Blender 脚本）。

## 6. 统一超分接口放在自己的命名空间，而不用 SRP 的实验框架

| 项 | 内容 |
|---|---|
| 选了 | 自己的包 `com.zfw.upscaling`，命名空间 `Zfw.Upscaling`，接口 `IUpscaler`（Initialize / GetJitter / GetMipBias / RecordPass / ResetHistory） |
| 备选 | SRP Core 里自带的 `IUpscaler` / `AbstractUpscaler` 框架 |
| 为什么 | 调查结论（`docs/调查-URP超分能力.md`）：SRP 那套框架被宏 `ENABLE_UPSCALER_FRAMEWORK` 关着，是**实验性**的，API 可能随版本变。自己的接口稳定，游戏只依赖它。 |
| 代价 | 对说明书 FR-UP-01 有一处偏离：三个内置后端的 `RecordPass` 是空的——放大 Pass 由 URP 自己在后处理里记录。补偿措施：`Initialize` 返回的尺寸换算成 `renderScale` 写进管线资源，冒烟测试核对 URP 实际渲染宽度和它一致，"唯一尺寸来源"仍然成立。 |
| 以后要换 | 设计文档里写好了：DLSS / FSR 2/3 / MetalFX 后端同时实现我们的 `IUpscaler` 和 SRP 的 `AbstractUpscaler`，打开那个宏，由 URP 在 STP/TAA 的位置调用。游戏层不改。 |

> 类比：商场的统一收银接口还在试运行（实验框架），随时可能改规则，所以先用自己的收银台，等商场的正式上线了再接过去。

## 7. 三个后端（STP / FSR 1 / 渲染缩放）及选择顺序

| 项 | 内容 |
|---|---|
| 选了 | 顺序 **DLSS → MetalFX → STP → FSR 1 → 渲染缩放**，取第一个"本机支持且本版有实现"的 |
| 为什么这个顺序 | 厂商专用的（DLSS、MetalFX）通常质量最好，放最前；**STP 在 FSR 1 前**：STP 是时间性的（利用多帧信息恢复细节），FSR 1 只是单帧放大加锐化；渲染缩放（线性放大）是保底，任何设备都能跑。 |
| 实测支持 | M5 Max 上 STP 质量档 FLIP 0.111，FSR 1 和渲染缩放都是 0.140，STP 在 6 个场景全部最好。 |
| 代价 | STP 需要计算着色器，比 FSR 1 贵一点（同档位 GPU 时间差在测量噪声以内）。 |
| 以后要换 | 顺序是选择器里的一个数组；可以改成"按实测结果推荐"（评估报告已经算出推荐：STP 平衡档），但目前自动档位仍按说明书映射（高档 → 质量档）。 |

## 8. DLSS / MetalFX / FSR 2/3 只做设计的原因

| 项 | 内容 |
|---|---|
| 现状 | 📄 只写了设计文档 `docs/设计方案/FSR2-3与DLSS-MetalFX后端.md`；选择器里留了名字位置，没有实现 |
| 原因 | ① **都需要原生插件**：DLSS 用 NVIDIA 的模块，FSR 2/3 要自己编译 FidelityFX SDK 成原生插件（C++），MetalFX 要写 Objective-C++ 插件——每一个都是独立的工程量。② **开发机是 Mac**：DLSS 只能在 Windows + RTX 上第一次运行和调试，FSR 2/3 官方没有 Metal 后端。③ URP 17 的超分框架还是实验性的（见第 6 条）。④ 项目周期 3 天，说明书允许这部分只做设计。❓（④的"允许"出自 PRD/最终指令，面试前可再翻一下原文确认措辞） |
| 设计要点 | 每个后端：`IsSupported` 先看 GpuCaps schema 2 的 `dlss / fsr / metalfx` 字段，再查自己的 SDK；初始化失败记日志并**自动退回下一个**，不能崩；抖动换 Halton(2,3)，相位数 8×(显示/渲染)²（数学已实现并有测试）；原生调用通过 `CommandBuffer.IssuePluginEventAndData` 在渲染线程执行。 |
| 验证计划 | DLSS 在 5060 Ti、FSR 2 在 1070 Ti、MetalFX 在 M5 Max 上测，直接复用 UpscaleBench。 |

## 9. 抗锯齿方案

| 项 | 内容 |
|---|---|
| 选了 | 关 / TAA / STP 三选一，默认 STP（低档默认 TAA）；**MSAA 全档关闭** |
| 备选 | MSAA、FXAA、SMAA |
| 为什么 | ① 时间性抗锯齿（TAA/STP）能处理草叶、树枝这类细小几何体的闪烁，MSAA 只处理几何边缘而且贵。② 超分本身就是时间性的，**STP 原生分辨率时就等于"更好的 TAA"**，降分辨率时直接变成超分，一套机制。③ 避免重复抗锯齿（IN-01）：STP 取代 TAA，不叠加。 |
| 关键实现细节 | URP 17 里把放大滤镜设成 STP 后，即使渲染比例 100% 也会跑 STP。时间性模式的前提：相机开后处理、关 MSAA、关动态分辨率、渲染器支持运动向量——`AntiAliasing.ApplyTo` 每次切换都强制设好。 |
| 代价 | 时间性方法的通病：快速运动时有残影风险，所以要准确的运动向量和及时清历史帧。 |
| 踩过的坑 | STP 资源在打包时被剥离导致黑屏（见 05）。 |

## 10. 画质分级的扩展机制

| 项 | 内容 |
|---|---|
| 选了 | 复用 `com.zfw.qualitytiers`（四档：低 / 中 / 高 / 极高），**不改共享包**，用包里预留的 `TierExtension`（`[SerializeReference] List<TierExtension>`）挂游戏自己的 `WildPartnerTier` |
| 扩展了什么 | 草地距离/密度、LOD 偏移、SSAO 开关、湖面反射探针分辨率、默认抗锯齿 |
| 为什么 | 多个游戏/模块可以各挂各的扩展，已有资产不用换脚本类型（比"让游戏继承 TierSettings"灵活）。 |
| 代价 | 扩展数据是多态序列化，编辑器里调试稍麻烦；档位资源里没放扩展时用代码里的默认表兜底。 |
| 以后要换 | 加新参数只改 `WildPartnerTier`，共享包不动。 |

> 类比：标准套餐（共享包）不变，但每家分店可以在套餐上加自己的"本店特色"小卡片（扩展）。

## 11. GRD（GPU Resident Drawer）的接入与 Mac 上未跑通的处理

| 项 | 内容 |
|---|---|
| 是什么 | Unity 6 的功能：把大量静态物体的绘制交给 GPU 批量完成，减少 CPU 提交绘制命令的开销 |
| 接入 | 前提都配好了：Forward+、BRG 变体全保留（`m_BrgStripping: 1`）、着色器带 DOTS Instancing。开关：设置菜单、F3 面板、启动参数 `-grd=` / `-occlusion=`；对比脚本 `tools/grd.sh` |
| 结果 | ❌ **Mac（Metal）上未达成**：打开后交给 GRD 画的物体全都不显示。排查到最小场景（只留一台相机、一盏灯、一个 URP 自带材质的方块）也复现，根因未找到。✅ 用户 11-24 在 **Windows DX12 上手动试玩确认开启后效果正常**（没有采集 Draw Call 对比数据）。 |
| 处理 | 按 PRD 的退路：开关保留、**默认关闭**、报告如实写"未达成"（`docs/GRD评估报告.md`）。 |
| 代价 | 默认关闭意味着 CPU 绘制提交开销没降下来（这也是 1070 Ti 机器上 CPU 占用偏高的可能原因之一）。 |
| 以后要换 | 按平台默认：DX12 默认开、Metal 默认关；同时继续用最小复现场景排查 Metal 问题（下一步：Xcode GPU 帧捕获看 BRG 的绘制命令是否发出、实例数据缓冲是否为空 ❓）。 |

## 12. 复用《矿坑余烬》的包（Git URL + 版本标签）

| 项 | 内容 |
|---|---|
| 选了 | `Packages/manifest.json` 里用 Git URL 引用，带版本标签：gpucaps `#v0.3.0`、qualitytiers `#v0.2.0`、perfrunner `#v0.3.1` |
| 备选 | 复制代码进项目；本地路径引用；搭私有包服务器（npm registry） |
| 为什么 | ① 不复制代码，一份源码两处用；② 标签锁版本，另一个项目改了也不影响这里；③ 需要改包时在原仓库改、打新标签、这里改一行 URL（实际发生过：GpuCaps 加 schema 2 → v0.3.0；PerfRunner 加超分参数 → v0.3.1）。 |
| 代价 | **MineEmbers 仓库目前是私有的**，别人克隆源码后 Unity 拉不到这三个包，打不开工程。要公开源码给面试官编译，需要把 MineEmbers 也设为公开。 |
| 以后要换 | 换成私有包服务器只改 manifest。 |

> 类比：不是把别家的菜谱抄一份，而是订阅"某版本的菜谱"，对方出新版你决定要不要升级。

## 13. 小地图用烘焙贴图，而不是实时相机

| 项 | 内容 |
|---|---|
| 选了 | 编辑器里用 `MapBaker` 预先烘焙一张世界地图贴图（`Resources/Map/WorldMap`），小地图和大地图（M）都画这张图，加图标 |
| 备选 | 俯视的第二台相机实时渲染到贴图 |
| 为什么 | 实时相机等于**每帧多画一遍场景**（又一次剔除、绘制提交、渲染），在已经偏 CPU 瓶颈的游戏里很贵；烘焙图只是几个 UI 四边形，几乎零成本，而且风格统一、可以手动加标注。 |
| 代价 | 地图不会反映实时变化（昼夜、天气、移动的动物）；改了世界布局要重新烘焙。 |
| 以后要换 | 想要实时信息就叠加图标层（已经这样做了：玩家箭头、伙伴位置），而不是换成相机。 |

## 14. Windows 包在 Mac 上交叉编译（Mono + DX12）

| 项 | 内容 |
|---|---|
| 选了 | 在 Mac 上直接打 Windows 64 位包，脚本后端 **Mono**，图形 API 只开 **D3D12**（Mac 只开 Metal） |
| 备选 | IL2CPP（把 C# 转成 C++ 再编译，运行更快）；在 Windows 机器上打包；CI 云打包 |
| 为什么 | IL2CPP 打 Windows 包需要 Windows 上的 Visual Studio 编译工具链，Mac 上做不了；而开发和测试流程都在 Mac 上自动化。DX12 是 PRD 要求。 |
| 代价 | ① Mono 的 C# 执行比 IL2CPP 慢（CPU 偏高的另一个可能原因）；② 打包机上没法运行 Windows 包，只能拿到 Windows 电脑上测（所以做了一键测试包 `tools/win/*.bat`，结果按显卡名分文件夹带回）。 |
| 以后要换 | 有 Windows 打包机或 CI 后，改成 IL2CPP 只改一个设置；`ProjectSetup.cs` 是"配置即代码"，可重复执行。 |

## 15. 运行时冒烟测试（在打包好的游戏里跑）

| 项 | 内容 |
|---|---|
| 选了 | `-smoketest` 启动参数：在**打包后的游戏**里，通过和玩家一样的入口（UI、按键）自动跑完整流程，输出 93 个步骤的 PASS/FAIL 和截图（`tools/smoke.sh`）。每次提交前必须通过。 |
| 备选 | 只用编辑器里的单元测试（EditMode / PlayMode） |
| 为什么 | 很多问题**只在打包后出现**：最典型的是 STP 资源被打包剥离导致黑屏，编辑器里完全正常。单元测试也有（超分包 EditMode 测试 7 个：选择器、档位映射、Halton、mip 偏移公式等），两者互补。 |
