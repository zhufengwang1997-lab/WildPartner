## 案例 1：室内木门"发光"，盖住女巫（NaN 被泛光放大）

**现象**：木屋里，门那一块是一大团白光，女巫走过去会被盖住，像门在发光。

**假设**（用户列的 + 自己想的）：
1. 门材质有自发光；
2. 室内的太阳没关；
3. 反射探针或光照探针把亮光带进来；
4. 门模型法线反了；
5. 某个像素算出了 NaN（非数），被后处理放大。

**验证**：
- 门材质：自发光 0，用 Toon 着色器，受光照影响。排除 1。
- 室内太阳：已关，强度 0。排除 2。
- Toon 着色器不采样反射探针；室内环境光设成暖色。排除 3。
- 门模型法线逐个检查：没有零或 NaN。排除 4。
- 往门**背后**查：有两块代码生成的网格，门板背板 `DoorBacking` 和拱形填缝 `DoorArchInfill`。

**根因**：
1. 这两块网格的"双面"写法是**同一组顶点配正反两组三角形**。`RecalculateNormals` 会把一个顶点所在的所有三角形的法线加起来，正面 + 反面 = 0。
2. 着色器对零向量做 `normalize`，就是 0/0，得到 NaN。
3. NaN 像素在门板裂缝里本来只是黑点，但**泛光（Bloom）会把它扩散成一大团白光**。

**修复**：
1. 正反两面各用一组顶点。
2. 双保险：Toon 着色器主光照和 DepthNormals 两处 `normalize` 改成 `SafeNormalize`（`Shaders/Toon.shader:131`），零向量不再变 NaN。
3. 冒烟测试加一项：室内所有可读网格不能有零或 NaN 法线。

**结果**：✅ 门不再发光（M5 Max 截图）。顺带发现室内屋顶两块坡顶旋转方向反了，一起修掉。

**延伸**：这个坑之前修鱼尾时也遇到过，第二次遇到就把它做成了自动检查。时间性超分会把 NaN 带进历史帧，拖好几帧，所以对超分项目更要防。

**面试时一句话**："看起来是光照问题，实际是 NaN 被 Bloom 放大。我先按'材质 → 光源 → 探针 → 法线'逐项排除，再往门后面找，发现是双面网格法线相加为零。修了网格、改了 SafeNormalize，再加自动检查，防止第三次。"

## 案例 2：打包后切到 STP 黑屏

**现象**：编辑器里 STP 一切正常；打包后切到 STP，画面停在黑屏或上一帧，日志每帧报 `STP.Execute` 空引用。

**假设**：
1. 机器不支持 compute shader；
2. 相机设置不对（MSAA、动态分辨率）；
3. 打包时资源缺了。

**验证**：
- 同一台机器在编辑器里能跑 STP，排除 1。
- 日志是空引用，说明某个资源对象是空的，指向 3。
- 查 URP 的打包流程，找到 `STPResourceStripper`：打包时检查所有管线资源，**没有一份的放大滤镜选 STP**，就把 STP 的计算着色器从包里删掉。
- 我们四档 URP 资源存的都是"自动"，运行时才改成 STP，打包时看不到。

**根因**：URP 打包优化把"看起来没人用"的 STP 资源剥离了。

**修复**：
1. 四档 URP 资源**存档时**放大滤镜都写 STP（`m_UpscalingFilter: 4`），打包时保留；运行时 `AntiAliasing.Apply` 再按玩家选择改回"自动"。
2. 每台相机渲染前检查一次抗锯齿设置（`beginCameraRendering`），因为游戏场景的相机比设置加载得晚。只要管线是 STP、相机还是"无抗锯齿"，URP 17 就会无历史地跑 STP，每帧报错。
3. 冒烟测试加一条：**全程不能有任何异常或错误日志**。原来只查逻辑，截图黑了也会通过。

**结果**：✅ Mac 包 STP 正常；Windows 1070 Ti 用户确认超分方案能切换、有效果。

**延伸**：后来 GRD 也用同一个办法（资源里存开启、运行时按设置关）。

**面试时一句话**："编辑器正常、包里黑屏，第一反应查打包剥离。URP 按资源里的设置决定保留什么，所以资源要'存'成最大需求，运行时再降。"

## 案例 3：Mac 上打开 GRD，交给 GRD 的物体全部消失（未解决）

**现象**：打开 GPU Resident Drawer 后，树、灌木、岩石、家具都不显示；关掉恢复。

**假设与验证（按时间顺序）**：

| 轮次 | 假设 | 验证 | 结果 |
|---|---|---|---|
| 1 | GPU 遮挡剔除误剔 | `-occlusion=off` | 仍然消失，排除 |
| 2 | Toon 着色器不兼容 DOTS Instancing | 镜头前放两个方块：URP Lit 和 Toon | 当时 Lit 方块"能显示"，Toon 不显示 → 以为是 Toon 的问题 |
| 2' | **复查对照组** | 发现 Lit 方块其实是**粉色错误着色器**（URP Lit 材质没进包），错误着色器不走 GRD | **第 2 轮的结论作废** |
| 3 | 对照组修好后 | Lit 材质放进 `Resources/` 保证进包 | Lit 和 Toon **两个都不显示** |
| 4 | 游戏里别的东西干扰（自定义 Pass、超分） | `-grdminimal`：关掉整个游戏，只留新相机 + 灯 + 两个方块；也试了原生分辨率、关抗锯齿 | 仍然都不显示 |
| 5 | GRD 实例反复重建 | 运行时监测 60 帧 | 重建 0 次，排除 |
| 6 | 着色器编译失败或变体被剥离 | 查打包日志、玩家日志；BRG 变体设成全保留 | 没有错误或警告 |

**根因**：❌ 未找到。能确定的是：**不在我们的物体、着色器或自定义渲染 Pass 上**（最小场景 + URP 自带 Lit 也复现）。

**处理**：
- 按需求文档的退路：开关保留、默认关、报告写"未达成"（`docs/GRD评估报告.md`）。
- 没有画出物体时 Draw Call 自然变少，这种数字**不能当成果**，所以 Draw Call 降低没有报。

**Windows 上的情况**：用户在 1070 Ti（DX12）上目测，打开 GRD 和遮挡剔除"有正常效果"。所以很可能是 Metal 发布版特有的问题。🟡 Windows 上还没有 Draw Call 对比数据（测试包 `grd` 那一项的结果还没拿回来）。

**还没做的下一步**：
- 在编辑器播放模式下试（编辑器里 GRD 有更多校验和日志）；
- 用 Xcode 的 Metal 帧捕获看 GRD 的绘制命令发没发出去。

**面试时一句话**："这个案例我最想讲的是对照组。第一轮我得出了错误结论，因为对照方块用的是错误着色器，它根本不走 GRD。发现后我推翻了结论，用最小场景把问题范围缩到引擎或平台层，然后按退路默认关闭，没有拿错误的 Draw Call 数字充成果。"

## 案例 4：挂机 10 分钟 GC 512 次

**现象**：TC-10 挂机测试（1920×1080，高档，STP，10 分钟自动走跑、切天气）帧率稳定，但全程 GC 512 次，最慢一帧 25.0 ms。

**假设**：每帧有小的托管内存分配，常见来源：LINQ、带捕获的 lambda、字符串拼接、`OnGUI`、`Transform.name`。

**验证（不靠猜）**：
- 发布版拿不到"每帧 GC 分配"，所以改打 **Development 包**。
- 用 `-profiler-enable -profiler-log-file` 把 Profiler 数据写成文件。
- 在编辑器里用 `HierarchyFrameDataView` 遍历调用树，把每个 `GC.Alloc` 记到它的调用路径上（`Assets/_Game/Editor/ProfileAllocReport.cs`，一条命令 `tools/allocprof.sh`）。
- 只看主线程、最后约 2000 帧。注意这 2000 帧里含退出过程，退出时一次性的分配会被平均进来（URP 资源 OnDisable 约 371 B/帧就是这个）。

**根因（按大小）**：

| 来源 | 每帧约 | 原因 |
|---|---|---|
| `SaveData.HasCaught` | 1.2 KB | `caught.Exists(c => c.id == id)`，lambda 捕获了 `id`，每次调用 new 一个闭包；每只动物每帧调一次 |
| F3 调试面板 | 370 B | 只要有启用的 `OnGUI`，Unity 每帧跑 IMGUI，面板隐藏也分配 |
| 月光花 | 300 B | 猫不在时每帧 `PetSwitcher.Pet`（场景查找 + LINQ） |
| 头发裙摆 | 少量 | 每帧读 `Transform.name`（每次新建字符串） |
| 小地图 | 少量 | 指南针方向数组每帧 new |

**修复**：
- lambda 改普通循环（`Scripts/Core/SaveSystem.cs:37`，`CreatureDefs.Get` 同样改）；
- `OnGUI` 挪到单独组件 `DebugOverlayGUI`，只在面板显示时启用；
- 找不到猫就 1 秒后再找；
- 裙摆在建链时记下名字；
- 方向数组改静态。

**结果**：✅（M5 Max）

| | 修前 | 修后 | 数据 |
|---|---|---|---|
| 每帧分配（含退出） | 2582 B | 506 B（稳态约 135 B） | `bench_results/allocprof-mac-20261123/before.txt`、`after.txt` |
| 10 分钟 GC 次数 | 512 | 69 | `bench_results/soak-mac-20261123/`、`soak-mac-20261123-gcfix/` |
| 最慢一帧 | 25.0 ms | 21.8 ms | 同上 |
| 第 1 分钟 → 最后 1 分钟帧率 | 118.0 → 117.9 | 120.0 → 119.9 | 同上（垂直同步 120 Hz） |

剩下约 84 B/帧在 URP 渲染图内部，不改引擎包。

**面试时一句话**："GC 不靠猜，靠 Profiler 数据定位到调用路径。最大的一项是一个带捕获的 lambda，每只动物每帧一次，改成普通循环。512 次降到 69 次。"

## 案例 5：树冠"马赛克"，一块块的

**现象**：用户反馈树冠近看是一块一块的色块，像马赛克。

**假设**：
1. 减面减太多，面片太大；
2. 没有抗锯齿，边缘闪；
3. 贴图分辨率不够；
4. 法线问题：每个面片法线朝向乱，在卡通色阶下被放大。

**验证**：
- 用户原始树模型约 4.8 万面，入库时减过面。→ 1 有一部分。
- 贴图原图是 4096，导入上限设成了 2048。→ 3 有一部分。
- 卡通着色把 N·L 量化成几档平色：**法线稍有差别，就可能跳到另一档颜色**。树叶模型每片法线方向都不一样，整个树冠就变成碎色块。→ 4 是主因（DECISIONS C1）。
- 当时还没做时间性抗锯齿（抗锯齿是后来超分阶段才加的）。它对树冠边缘闪烁有帮助，但对"大块色块"这个现象帮不上，因为色块不是锯齿。❓ 抗锯齿对树的改善没有单独量化。

**根因**：主要是卡通色阶 + 杂乱的叶片法线；减面和贴图上限加重了它。

**修复**（提交 839cc7b）：
1. LOD0 直接用原始 4.8 万面不减面，后面三级 1.4 万 / 4000 / 1000。
2. **树冠顶点法线改为"绕树冠椭球的法线"**：80% 椭球法线 + 20% 原法线。树干保持原法线。这是卡通渲染常用的"球形法线"技巧，整棵树冠像一个光滑的球那样受光。
3. 贴图上限 2048 → 4096。

**代价**（M5 Max，1600×900，同一机位 3 秒平均）：森林机位 2.3 → 3.8 ms，草地 1.7 → 2.4 ms。

**结果**：✅ 前后对比图在 `docs/screenshots/feedback-1123c/C1_*`。

**面试时一句话**："马赛克看着像减面问题，主因其实是卡通色阶对法线太敏感。用椭球法线让树冠整体受光，再把 LOD0 换回原模型。代价是森林机位多了 1.5 ms，有测量。"

## 案例 6：超分评估里，同一后端的质量档比性能档还差

**现象**：第一次跑 `UpscaleBench`，某个后端的质量档（渲染 67%）FLIP 比性能档（50%）还大。不合常理。

**假设**：
1. 质量档真的有问题；
2. 每个配置拍到的画面内容不一样。

**验证**：对比两张截图，草叶的位置不一样。风动时钟在配置之间一直往前走，每个配置拍到的是不同相位的风。

**根因**：测试不可复现。FLIP 量到的主要是"风吹到哪了"，不是超分画质。

**修复**：
- 每个配置开始时风时钟归零（`EnvController.ResetWindClock`）。风照常吹，所以时间性超分仍要处理真实运动，只是起点一致。
- 同时固定帧步长 `captureFramerate = 60`、随机种子 1123、每个配置清历史。

**结果**：✅ 修后 STP 质量档 6/6 场景都比性能档好，排序合理。

**面试时一句话**："数据不合常理，先怀疑测试本身。风的相位没对齐，FLIP 量的是风。"

## 案例 7：推荐规则把"不抗锯齿"算成了基线

**现象**：推荐规则是"FLIP 不超过最佳原生抗锯齿的 110%，取帧率最高"。结果最佳原生是 `native_off`（不抗锯齿），预算被压得很紧。

**分析**：
- `native_off` 不是抗锯齿，不该算进"最佳原生抗锯齿"。
- 参考图是不带时间滤波的 2 倍超采样，单帧 FLIP 天然偏向同样没有时间滤波的 `native_off`。
- 但 `native_off` 的闪烁（时间稳定性 0.00822）约是 STP（0.00376–0.00396）的 2 倍。

**修复**：基线只算 `native_taa` / `native_stp`，`native_off` 不参与推荐（`Tools~/bench_report.py:66`）。

**关键**：这是**修正定义错误**，不是看了结果再调规则。报告里写明了这一点。

**结果**：推荐 **STP 平衡档**（FLIP 0.1168 ≤ 0.1069 × 1.1，173 FPS）。游戏的自动档位仍按说明书（高档 → 质量档），推荐只作参考。

**面试时一句话**："改规则前我先问自己：是定义错了，还是我想要另一个结果？这里是定义错了：不抗锯齿不是抗锯齿。我在报告里把这一点写明了。"

## 案例 8：三种抗锯齿帧时间一模一样 8.3 ms

**现象**：第一次对比"关 / TAA / STP"，三个都是 8.3 ms。

**根因**：8.3 ms = 1/120 秒，是 120 Hz 屏幕的**垂直同步间隔**。GPU 早就画完了，在等屏幕刷新。量到的是"等"，不是"画"。

**修复**：统一用 `GpuTimer`：关垂直同步、不限帧率，取 FrameTimingManager 数据，去掉最慢 10%。

**面试时一句话**："测性能第一件事是关垂直同步，否则量到的是屏幕刷新率。"

## 案例 9：Metal 上 GPU 时间约是帧时间的 2 倍

**现象**：FrameTimingManager 的 GPU 帧时间，比实际每帧耗时还大。例如参考配置 GPU 25.89 ms，帧时间 11.93 ms。

**根因（推测）**：Metal 上这个值包含多帧并行时的排队时间。❓ 具体机制待确认，现象在所有配置上一致。

**处理**：
- GPU ms 只用来比较配置之间的相对高低；
- 对外报告的 FPS 用实际帧时间；
- 报告里每张表都写了这条说明。

**面试时一句话**："一个计数器读出来不合理，先别用，查清它量的是什么；查不清就只用它的相对值，并在报告里写明。"

## 案例 10：开局镜头从天上飞下来、穿过地形

**现象**：游戏一开，镜头从山谷上空飞向木屋，中途穿过地形。

**第一次修**（提交 05e7498，11-24 00:20）：删掉主菜单绕山谷旋转的镜头，在 `Update` 里把主菜单相机优先级改成 0。用户在 Windows 上用这一版的包试玩，反馈**穿模动画仍然存在**。

**根因**：主菜单相机在场景里优先级是 20。Cinemachine 的"大脑"在**第一帧**就看到它是最高优先级，于是从它混合到玩家相机，混合 2 秒。等 `Update` 改优先级时，混合已经开始了。

**修复**（提交 30135df，11-24 08:51）：在 `Bootstrap.Awake` 里直接把主菜单相机的物体关掉，Cinemachine 大脑永远看不到它（`Scripts/Core/Bootstrap.cs:33`）。开场直接是女巫在床上醒来。

**结果**：✅ Mac 冒烟第 1 步"启动后直接在木屋床上醒来"通过。🟡 Windows 上是否已消失，要等用户用新包确认。

**面试时一句话**："第一次修在了错误的时机。Cinemachine 第一帧就决定混合，所以要在它看到之前（Awake）就关掉。"

## 案例 11：设置菜单显示不全；切页后显示的是别页的行

**现象**：
1. 设置菜单下面几行被截掉；
2. 加了分页以后，切页偶尔显示旧页的行。

**根因**：
1. 12 行约 790 px，列表区只有 560 px，跟显卡无关，纯布局问题。小分辨率下更糟。
2. 清旧行时**一边遍历 Transform 的子物体、一边把它们移走**。每移走一个，后面的序号就往前挪一位，所以每隔一个会漏掉一个。

**修复**：
- 分四页（显示 / 画面 / 操作 / 声音），加 `ScrollRect + RectMask2D` 滚动；
- `CanvasScaler` 改 `Expand`，适配任意宽高比；
- 清行时先把子物体收集到列表再删。

**验证**：✅ `tools/uishots.sh` 在 6 种分辨率（1280×720、1366×768、1920×1080、2560×1440、1920×1200、3440×1440）× 9 个界面截图检查（`docs/screenshots/ui-res/`，M5 Max）。

**面试时一句话**："UI 问题也要在多种分辨率上自动截图，不能只看自己的屏幕。"

## 案例 12：河面的纹理往上游流

**现象**：河水看起来在倒流。

**根因**：水面着色器里法线贴图的采样坐标是 `p + flow × t`，图案往上游走；流纹那一项是 `− t`，方向是对的。两者打架。

**修复**：
- 统一成 `p − flow × t`。
- 流速按河道控制点给系数（瀑布下 1.7–1.8，往湖口降到 0.12，湖里 0），写进河面网格的第二套 UV。
- 着色器用两相位交替淡入淡出，这是 flow map 的常用做法，避免流速不均时贴图被越拉越长。
- 同一张流速表（`WorldLayout.RiverFlow`）给漂浮物、鱼群、游泳推力共用，保证看到的和感受到的一致。

**面试时一句话**："一个符号错误。修的时候顺便把流速做成一张表，画面和物理共用同一份数据。"

## 案例 13：攀爬时镜头被"树挡住"

**现象**：冒烟截图里，女巫爬塔时画面被一棵树挡住。

**验证（先查清是什么挡住）**：截图那一刻记下镜头位置、她的位置、附近树冠包围框、镜头处的碰撞体。

**根因**：镜头其实**挤进了塔墙里**（冒烟把镜头摆在她侧前方，防遮挡组件因为她离墙太近没把镜头推出来）。画面里的树是她头顶那棵。

**修复**：
1. 攀爬时镜头自动转到她身后、对着墙。玩家转过镜头后 1.2 秒内不抢。
2. 树冠不加碰撞体（会影响攀爬射线），改为生成时记下每棵树冠的包围框，由 Cinemachine 扩展 `CanopyCameraAvoid` 沿"看点 → 镜头"检测，拉近到第一个树冠前。只在攀爬、翻越或离地 3 m 以上时启用。

**面试时一句话**："先记下现场数据再修。看起来是树挡住，实际是镜头进了墙。"

## 案例 14：Windows（i7-6700 + 1070 Ti）上 CPU 占用约 43%（未测量）

**现象**：用户在任务管理器看到：CPU 42.7%，内存 892.5 MB，GPU 1.7%。

**假设**（❓ 全部是推测，没有测量）：
1. Unity 的工作线程在空闲时"自旋等待"，会占 CPU 但不干活；
2. 这个游戏本身偏 CPU 瓶颈（Mac 上超分只提升 33–42%，报告里推测接近 CPU 瓶颈）；
3. GRD 默认关闭，所有物体走 CPU 提交；
4. 声音是运行时程序化合成的；
5. Mono 脚本后端（不是 IL2CPP）；
6. i7-6700 是 2015 年的 4 核 8 线程 CPU。

**疑点**：GPU 1.7% 这个读数很可疑。任务管理器默认看的是 "3D" 引擎，可能没统计到 DX12 的实际负载。❓ 待确认。

**要验证需要做的**（都没做）：
- 用 Unity Profiler 连上 Windows 包，看主线程和渲染线程各花多少；
- 打开垂直同步 / 限帧再看 CPU 占用；
- 测试包里的基准数据拿回来后看帧时间。

**面试时一句话**："任务管理器的百分比不能当性能数据。我列了几个可能原因，但没有测，不下结论。要用 Profiler 看线程时间线。"

## 总结：这些案例共同的方法

1. **先复现、先记录现场**，再猜原因（案例 1、13）。
2. **对照组要可信**：对照组本身错了，结论全错（案例 3）。
3. **测试要可复现**：固定风、随机种子、帧步长、历史（案例 6）。
4. **知道每个计数器量的是什么**：垂直同步、Metal 排队、任务管理器（案例 8、9、14）。
5. **修完要加自动检查**，防止第二次（案例 1、2、11）。
6. **没查清就老实写"未找到"**，不用错误数字充成果（案例 3、14）。
